Releases guide
How to prepare, check, and publish records and documents

This guide is for experiment curators. A release is the bundle of records and documents you check on the portal before they become public.

Your CERN account needs a role whose name ends in -curator, for example cms-curator. After you log in, open the menu under your email address. Each experiment you curate is listed there, such as CMS releases. This guide is in the same menu.

The releases list

Open your experiment from the account menu. The page lists the releases for that experiment.

  • Filter by name, or by step: Draft, Staged, or Published.
  • Show published releases is ticked by default. Clear it when you want the list limited to work still in progress.
  • Click a column heading to sort.
  • A red number beside the step is how many check errors that release still has.
  • Open discussion leaves the portal and opens the forum thread, when the release has one. Clicking the rest of the row opens the release.

Creating a release

Create new release builds a release from JSON. Choose Upload JSON file or Load from URL. The address has to return JSON.

The file can be any of these:

  • one record, or a list of records
  • one document, or a list of documents
  • one object with records, documents, or both, plus an optional name, description, and discussion_url

A document is a JSON object with a slug or a body, and without a recid or files. Everything else is read as a record. If you leave out name, the release takes the file name, or the last part of the URL. 

{
  "name": "CMS 2024 open data",
  "description": "Collision data and the notes that go with it.",
  "discussion_url": "https://opendata-forum.cern.ch/t/example",
  "records": [],
  "documents": [
    {
      "slug": "cms-2024-notes",
      "title": "CMS 2024 notes",
      "body": {
        "content": "# CMS 2024 notes\n\nWrite the guide here."
      }
    }
  ]
}

You can add further records and documents after the release exists. Download release saves JSON in this same shape, so you can edit it and upload it as a new release. Fields the portal fills in for itself are omitted from that download.

Draft, staged, and published

The bar at the top of a release shows three steps: Draft, Staged, and Published.

Draft

This is the working copy. You can change records, documents, and the release name, description, and discussion link. The step stays on Draft in two situations. While checks are failing, the status shown in parentheses is DRAFT and Stage Release is disabled. When every enabled check passes, the status becomes READY and Stage Release can be used.

Saving can take a moment, and the page then says the release is being edited. Staging, publishing, and returning to draft also run in the background. The page refreshes until they finish. If that message stays on the screen, the action failed and the release is put back with an error you can read.

Staged

A staged release is locked, so you can review it as visitors will see it. View on each row opens the record or document. Return to Draft unlocks it when something still needs to change. Publish makes the release public. The button asks you to review it carefully before you continue. While the release is staged you can also Generate DOIs for records that do not have one yet. A warning stays on the page until every record has a DOI.

Published

A published release stays locked. History and download still work. If a DOI did not register with DataCite, Retry sends those records again.

The menu beside the release title holds the rest of the actions:

  • View History lists each status change, with the time and the person who made it.
  • Download release saves the JSON described above.
  • Edit metadata changes the name, the discussion link, and the description.
  • Delete release is available while the release is DRAFT or READY.

Records

The Records tab lists the recid, the DOI, and the title.

  • Add Records takes one JSON file, or a URL that returns JSON. The file can hold one record or a list of them.
  • Edit Records opens every record together as JSON, under the heading Edit all records.
  • Bulk Edit applies one change across many records. Preview the difference first, then apply it. The preview shows the first 10 records.
  • Edit on a row opens that record. The editor has a form, the raw JSON, and a preview of the public page.
  • View works once the release is staged or published, and opens the record page.

A record id looks like cms-1234: the experiment name, a hyphen, then digits. Each recid has to be unique, and it cannot already be published. If a recid is missing or already taken, Fix automatically can assign one. A newly assigned id is marked in the table.

Documents

The Documents tab lists the slug, the title, and the type.

  • Add Document accepts JSON files, a folder of them, or a URL. body.content has to be the markdown text itself. A file name such as guide.md is rejected. Files in the folder that are not JSON are skipped.
  • Write links to other documents as /docs/their-slug. A bare slug is rewritten to that form when the target is already in the release or already published.
  • Upload Images attaches pictures to a document. Use PNG, JPG, JPEG, or GIF, up to 5 MB each. If that file name is already used for the document, rename it and upload again. Copy the path from the image row when the markdown needs to refer to it. You can edit or delete an image from that row.
  • Edit opens the document, including a preview of the public page.
  • View opens /docs/<slug> once the release is staged or published. On an image row it opens a preview of the file.

Checks

The Validations panel sits above the Records and Documents tabs while the release is still a draft. Failed checks are listed first, then optional checks you have switched off, then checks that passed. Beneath the list, the page shows up to 100 error lines and says how many exist in total.

Stage Release stays disabled until every enabled check passes. A check that only applies to records is hidden when the release has no records, and the same is true for documents. Experiment-specific checks appear only for that experiment.

Optional checks can be switched off for this release. A check marked Auto-fixable can be cleared with Fix automatically. The page then tells you what passes now, what you still have to correct by hand, and whether any record ids were assigned.

The names in the panel mean the following.

  • Valid record schema and Valid document schema. The JSON follows the portal schema.
  • Valid recid. Each record has a unique recid of the form experiment-number, and that id is free to use.
  • Valid slug. Each document has a unique slug that is free to use. A missing slug can be taken from the source file name.
  • Valid experiment. experiment on each record and document matches this release, for example CMS.
  • Valid standard fields. Records carry the usual publisher, CERN Open Data Portal, and license, CC0-1.0. These can be filled in for you.
  • File metadata. Each file has a size and a checksum written as algorithm:value.
  • Missing files. A record that says how many files it has actually lists them. A record that points at a Rucio dataset can omit the file list.
  • Duplicate files. File addresses in this release are new to the portal.
  • Expand directories. A file path that ends in * is a directory. It can be expanded into the files inside it.
  • Valid DOI. A DOI that is present is well formed, and its suffix is unique. On the production portal the prefix is checked as well. A broken DOI can be replaced with a new one. You can leave the DOI empty and generate it after staging.
  • Valid document links. A markdown link to /docs/... points at a document in this release or one already published. A bare slug that points at a known document can be rewritten for you. A link to an unknown document has to be corrected by hand.
  • Valid image references. An image cited in a markdown document is available. Upload the missing image, or correct the path.
  • CMS. On a CMS release, the collaboration is CMS Collaboration and the accelerator is CERN-LHC. These can be filled in for you.
  • CMS 2016 Simulated. An optional extra check for CMS 2016 simulated records. You can switch it off.
  • Rucio datasets. An optional CMS check. A record with a rucio_dataset and no file list can be expanded into its files. You can switch the check off.
